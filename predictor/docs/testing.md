# Тестирование ESB

## Уровни проверок

| Уровень | Команда | Что проверяется |
| --- | --- | --- |
| Модульные тесты | `make test-unit` | Правила предметной области, сценарии приложения, нормализация данных, повторы и частичные ошибки адаптеров на тестовых HTTP-серверах и заглушках. |
| Интеграционные и сквозные проверки | `make test-e2e` или `make test-integration` | HTTP, WebSocket и MCP API, а также взаимодействие ESB с PostgreSQL, ClickHouse и MinIO. Два процесса ESB используют общую PostgreSQL; две имитации Hermes проверяют лимиты и маршрутизацию. |
| Проверка с языковой моделью | `make test-llm-tools` | Необязательный запуск Савелия, Кеши и Константина через Hermes и ESB с изолированными хранилищами; проверяется фактический вызов моделью `get_company_profile`. |
| Полный набор | `make test` | Модульные тесты, затем изолированная интеграционная и сквозная проверка. |
| Проверка гонок | `make test-race` | Модульные тесты Go с детектором `-race`; сквозная проверка запускается отдельно через `make test-e2e`. |
| Покрытие | `make coverage` | Покрытие ESB модульными тестами по пакетам и общий результат. |
| Безопасность MCP | `make test` / `make test-e2e` | Раздельные токены, закрепление сессии за ролью, серверные списки разрешённых инструментов и отказ в доступе по токену Domain. |

Отдельного набора прямых интеграционных проверок репозиториев нет: сценарии PostgreSQL, ClickHouse и S3 проходят через публичный API ESB. Поэтому `make test-integration` — другое имя для сквозной проверки, которая поднимает изолированные сервисы. Проверки с имитациями не используют ключи языковой модели. Отдельный запуск с реальной моделью использует только локальный `LLM_API_KEY` из `predictor/.env` или окружения.

Все файлы `*_test.go` находятся в `predictor/tests/`. Модульные тесты подключаются к пакетам ESB через Go overlay; модуль сквозных проверок не компилирует их повторно.

## Требования к сквозной проверке

Нужны запущенные Docker Engine и Docker Compose v2. `make test-e2e` проверяет их до запуска. Файл `predictor/tests/compose.e2e.yml` создаёт отдельные контейнеры и тома для PostgreSQL, ClickHouse, MinIO, имитации Hermes и ESB. Скрипт применяет начальные миграции, ждёт проверки готовности, а после завершения удаляет контейнеры, сеть и тома.

При ошибке проверки скрипт выводит журналы только своего изолированного проекта Compose перед очисткой. В тестовых данных используются синтетические идентификаторы и учётные данные. Не добавляйте клиентские данные или реальные ключи в тестовые наборы и диагностические журналы.

## Проверка реальных вызовов MCP

`make test-llm-tools` использует отдельный проект Compose и временные PostgreSQL, ClickHouse и MinIO. Проверка пропускается, если не найден `LLM_API_KEY`. Она запускает не более четырёх обращений к модели: по одному для Савелия и Кеши, первичный анализ Константина и один вопрос через его WebSocket. Для каждого синтетического источника ESB также получает `POST /call?agent=serezha` через имитацию Hermes, чтобы создать связь источника с компанией в PostgreSQL, которую Константин проверяет при сохранении ссылок. Для повторов отправки ESB установлено значение `1`; `max_turns` тестовых агентов ограничен восемью.

Hermes передаёт MCP-запросы ESB через тестовый прозрачный прокси. Прокси сохраняет только имя инструмента, агента и синтетический `correlation_id`; аргументы, заголовки, ответы инструментов и тексты модели не записываются. Проверяются фактический вызов `get_company_profile`, его место перед сохранением результата, завершение вызова и ожидаемая запись или ответ. Для ответов Константина проверяется точный `source_id` синтетической новости и сохранённая история. Ответы модели могут меняться: отсутствие точной цитаты требует ручной проверки ответа и источников. Проверка не доказывает защиту от всех вариантов внедрения инструкций. При ошибке скрипт не выводит журналы контейнеров и удаляет только тома собственного проекта Compose.

## Покрытие кода

`make coverage` использует `go test -coverprofile` и `go tool cover` из установленного набора Go. Отчёт показывает покрытие каждого пакета ESB и общий процент. Временный файл отчёта хранится в системном временном каталоге только во время команды и удаляется после вывода результата.

Сетевой клиент сквозной проверки обращается к отдельному процессу ESB в контейнере. Этот бинарный файл не собран с инструментированием покрытия, поэтому сквозная проверка подтверждает поведение, но не увеличивает процент покрытия. Минимальный процент автоматически не задан: важнее проверить ошибки, повторы, границы данных и восстановление после частичного сбоя.

## Основные сценарии

- Терминальные и промежуточные статусы, допустимые типы метрик.
- Идентификаторы и периоды фактов, курсоры страниц, ограничения широких запросов.
- Принадлежность `metric_id` компании, конечность числовых значений и единицы измерения из PostgreSQL.
- Повторная синхронизация профиля после частичного сбоя S3 или PostgreSQL.
- Восемь одинаковых одновременных запросов `POST` с одним ключом идемпотентности создают один вызов PostgreSQL.
- Ошибки авторизации, некорректный JSON, превышение размера запроса и безопасные ответы при недоступности зависимости.
- Тайм-ауты и отмена запросов к Hermes и ClickHouse; ограниченные повторы HTTP-запросов через `httptest`.
- HTTP, WebSocket и MCP через ESB, история Константина и безопасная очистка данных.
- Распределение вызовов между двумя процессами ESB и экземплярами Hermes с ограниченной ёмкостью.
- Фактические вызовы MCP моделью проверяются только командой `make test-llm-tools`; имитации подтверждают маршрутизацию, но не действия модели.

## Надёжность тестов

Для синхронизации используйте каналы и сигналы готовности, не применяйте `time.Sleep`. Даты задавайте явно; порядок в JSON и Go map не считайте частью контракта. Для каждого тестового HTTP-сервера вызывайте `defer server.Close()`. Фоновые горутины должны иметь владельца, способ остановки и ограничение времени ожидания. Не проверяйте динамический текст ошибок драйверов: проверяйте тип ошибки или `errors.Is`, безопасный внешний статус и отсутствие утечки данных запроса или учётных данных.
